# Coordinate first, then ship small reader PRs

Bringing Jellyfin's web e-reader closer to KyBook 3 is technically modest work for an experienced developer but organizationally hard. The typography and theme controls KyBook users expect (font family, line height, margins, persisted themes, a scroll mode) can all be built client-side on the existing epub.js engine in roughly **1.5–3 weeks of coding for the first tier** and **2–4 more weeks for navigation features**. Bookmarks, highlights and precise sync require server schema work that has been stalled in API design for 11 months. The binding constraint is review, not code. In 2026, **none of the roughly eight outside book-reader PRs found was merged**, while the core maintainer who owns the reader, dkanada, landed his own refactor within days. Outside contributors who do get merged wait a **median of about 11 days, with a 75th percentile near 45 days**. jellyfin-web also enforces an LLM policy that closes non-compliant PRs without review. The realistic plan is to open an issue and agree scope with dkanada before writing code, then ship one setting per PR on top of his React `BookOsd` component, expecting first merges in 1–3 months and a 13.0 release around mid-to-late 2027. If you want KyBook-class reading now rather than in a year, the OPDS plugin with a maintained external reader gets you there today. Pair it with an upstream contribution only if you care about the built-in reader for its own sake.

## Jellyfin 12.0 re-skinned the reader but kept a 2022 engine

"V12" is Jellyfin 12.0, released 2026-09-08. The project dropped the `10.` prefix, so the planned 10.12.0 shipped as 12.0. Web 12.1 and 12.2 followed on September 15 and October 5 ([Jellyfin 12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/); [jellyfin-web releases](https://github.com/jellyfin/jellyfin-web/releases)). The release framed books as "the start of an effort" to stop them taking a backseat to video. It moved OPF and ComicInfo metadata into the server and deprecated the Bookshelf plugin. On the reading side it promised a reader "redesigned and standardized across all book types", working progress indicators, and better EPUB font sizing ([release post](https://jellyfin.org/posts/jellyfin-release-12.0/)). In practice the redesign was chrome rather than engine. dkanada migrated the on-screen controls to a shared React `BookOsd` component, unified fullscreen, added PDF swipe navigation and fade animations, and fixed the font-size CSS. The renderers themselves are unchanged: **epub.js 0.3.93** for EPUB, pdfjs-dist 3.11.174 for PDF, and libarchive.js plus Swiper for comics ([PR #7848](https://github.com/jellyfin/jellyfin-web/pull/7848); [PR #8004](https://github.com/jellyfin/jellyfin-web/pull/8004); [package.json @v12.2](https://github.com/jellyfin/jellyfin-web/blob/v12.2/package.json)).

The EPUB controls in v12.2 are previous/next, a table of contents, a three-way theme cycle (dark, a "sepia" that is tan text on black, and light), five keyword font sizes, fullscreen, arrow and J/L keys, and swipe. Paged layout is the only option, and the source still carries `// TODO: Add option for scrolled-doc`. Theme and font size are kept on the player instance only, so **they reset every time you open a book** ([bookPlayer/plugin.js @v12.2](https://github.com/jellyfin/jellyfin-web/blob/v12.2/src/plugins/bookPlayer/plugin.js)). There is no font family choice, line spacing, margins, bookmarks, highlights, search or zoom. Issue #6679 reports that zoom is blocked even on iPadOS, and it has been open since March 2025 ([#6679](https://github.com/jellyfin/jellyfin-web/issues/6679)). Reading position is a single percentage sent through the video playback pipeline, not an EPUB CFI, so a resumed book lands only approximately. On every open the reader rebuilds a location map, which one 2026 PR measured at **20 seconds** on a 6.75 MB omnibus ([PR #8423](https://github.com/jellyfin/jellyfin-web/pull/8423)). epub.js has had no npm release since February 2022. Its repo still merges a few fixes a year, including a 2026 fix for continuous-scroll jitter that Jellyfin cannot get without vendoring ([npm registry](https://registry.npmjs.org/epubjs); [epub.js commits](https://api.github.com/repos/futurepress/epub.js/commits?per_page=6)).

The iOS picture matters for you. Swiftfin, the native iOS app, does not support book libraries at all, and its docs call them "lower priority" ([Swiftfin libraries.md](https://github.com/jellyfin/Swiftfin/blob/main/Documentation/libraries.md)). On an iPhone or iPad, the only Jellyfin reader is jellyfin-web, either in Safari or inside the WebView-based mobile app. The web code has Safari-specific swipe handling and safe-area padding for that reason ([BookOsd.tsx @v12.2](https://github.com/jellyfin/jellyfin-web/blob/v12.2/src/plugins/bookPlayer/BookOsd/BookOsd.tsx)). One consequence: **any improvement to jellyfin-web reaches every web and WebView client at once**, so it is the highest-leverage place to contribute. A Swiftfin reader would be a new feature from scratch that its maintainers have deprioritized.

## Most of the KyBook gap closes client-side; the rest needs a stalled server API

KyBook 3 has been abandonware since v0.7.8 in February 2019, but it remains a useful benchmark ([App Store](https://apps.apple.com/app/id1348198785)). Its feature list covers configurable fonts, size, margins, paragraph indentation and backgrounds. It also has hyphenation and hanging punctuation, day, night and sepia themes, scroll, curl and slide page turns, plain, fuzzy and regex search, bookmarks and highlights with Markdown, HTML, PDF and RTF export, StarDict and DSL dictionaries, TTS, auto-scroll, and OPDS ([kybook-reader.com source](https://github.com/kolyvan/kybook-reader.com/blob/master/index.html)). Comparing against current readers such as Readest, KOReader, Thorium and Apple Books, the table-stakes set is: font family and size, line spacing, margins, light, dark and sepia themes, paged or scroll mode, TOC plus a progress indicator, bookmarks, highlights with notes, in-book search, synced position, dictionary lookup, TTS, and accessibility ([Readest](https://github.com/readest/readest); [KOReader](https://github.com/koreader/koreader); [Thorium](https://github.com/edrlab/thorium-reader)). Jellyfin 12.2 meets only TOC, partial themes, coarse font size and approximate position sync.

Almost every missing control maps onto an existing epub.js API. Fonts and sizes use `rendition.themes`, line height and margins use injected CSS, scroll mode uses `flow: 'scrolled-doc'` or the continuous manager, two-page spreads use `spread()`, search uses `section.find()`, and highlights use `annotations.highlight(cfiRange)` ([epub.js README](https://raw.githubusercontent.com/futurepress/epub.js/master/README.md)). Audiobookshelf already ships this pattern on the same library: a settings drawer with theme, font, a 5–300% scale, line spacing and spread, plus in-book search and CFI progress synced to its server ([ABS EpubReader.vue](https://raw.githubusercontent.com/advplyr/audiobookshelf/master/client/components/readers/EpubReader.vue)). Persisting reader settings needs no server change. jellyfin-web's `userSettings.set(name, value, true)` already writes to the per-user `DisplayPreferences.CustomPrefs` on the server, so settings would follow you across devices ([userSettings.js](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/scripts/settings/userSettings.js)).

The hard boundary is user data. There is **no server storage for bookmarks, highlights, notes, reading statistics or CFI positions**. Server PR #15633, which adds a single `ProgressState` column for precise EPUB positions, has been open since November 2025. dkanada has steered its review toward a general typed position object with `Page`, `Duration` and `Percentage` variants. On 2026-10-10 he asked the author whether they would pick it back up ([jellyfin PR #15633](https://github.com/jellyfin/jellyfin/pull/15633)). Any annotation feature therefore needs three things in order: a server entity with an EF Core migration and endpoints, a regenerated `@jellyfin/sdk`, and then the web UI ([jellyfin-sdk-typescript README](https://github.com/jellyfin/jellyfin-sdk-typescript/blob/master/README.md)). That is three repos and the core API design discussion that has already stalled one column for nearly a year.

The estimates below come from the research team's judgement for a competent web developer new to the codebase. They are calibrated against the 394-line `plugin.js`, the Audiobookshelf settings implementation, and the scope of #15633. Nothing was prototyped, so read them as order-of-magnitude.

| Tier | Features (KyBook equivalent) | Where it lives | Coding effort | Main risk |
|---|---|---|---|---|
| 1. Typography and themes | Persisted theme and size; font family; line height; margins; justify and hyphenate; custom colors; spread | Web only, `CustomPrefs` | **1.5–3 weeks** | Publisher CSS overriding settings, a known problem in the current code |
| 2. Navigation and UX | Scroll mode; tap zones; in-book search; page numbers; publisher-style override toggle | Web only | **2–4 weeks** | epub.js continuous-scroll bugs; a slide animation needs custom CSS; no page curl |
| 3. User data | Bookmarks; highlights and notes; CFI sync; reading stats | Server, SDK and web | **3–6 weeks**, plus about 1–2 weeks of server work per entity | Blocked on the progress-API redesign in #15633 |
| 4. Read-aloud and lookup | TTS through `speechSynthesis`; dictionary through an external link or Wiktionary | Web only | **2–3 weeks** | Browser voice coverage varies across TV and WebView clients |

Source for the tiers: [technical analysis of plugin.js](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/plugins/bookPlayer/plugin.js) and [PR #15633](https://github.com/jellyfin/jellyfin/pull/15633).

Some KyBook features are effectively out of reach in a browser reader: page-curl animation, Apple Pencil drawing, PDF OCR and reflow, MOBI, AZW3 and FB2 under epub.js, and bundled dictionaries. A renderer swap changes that calculus. **foliate-js (MIT)** parses EPUB, MOBI, AZW3, FB2 and CBZ in the browser. It switches between paged and scrolled mode without reloading and ships annotation, search, TTS, dictionary and footnote modules. Its README, however, says it is "not stable" and has no releases ([foliate-js README](https://raw.githubusercontent.com/johnfactotum/foliate-js/main/README.md)). The team estimates a parity rewrite at **1–2 weeks**, which would cut later-tier costs by perhaps a third. Readium's ts-toolkit is better maintained but likely needs a server-side streamer, so the estimate is **4–8+ weeks** ([ts-toolkit README](https://raw.githubusercontent.com/readium/ts-toolkit/develop/README.md)). All candidate licenses are compatible with jellyfin-web's GPL-2.0-or-later. A swap is still a maintainer-level architectural decision, not a newcomer's first PR.

## Review capacity and policy, not code, set the timeline

Setup is cheap. The web client needs Node 24 or later and npm 11 or later, then `npm install` and `npm start` against any 12.x server, such as a Docker container with a Books library. That is roughly an afternoon. Server work adds the .NET 10 SDK ([jellyfin-web README](https://github.com/jellyfin/jellyfin-web/blob/master/README.md); [jellyfin global.json](https://github.com/jellyfin/jellyfin/blob/master/global.json)). There is no CLA or DCO. Note that the official development docs still cite .NET 8/9 and Node 20, so trust the repo files instead ([Jellyfin docs: Development](https://jellyfin.org/docs/general/contributing/development)). The codebase is a hybrid. New files must be TypeScript, and new UI must be React using the Jellyfin TS SDK. The book player's `plugin.js` is still legacy JavaScript wired into the React `BookOsd` ([CONTRIBUTING.md](https://github.com/jellyfin/jellyfin-web/blob/master/CONTRIBUTING.md)).

The process rules are where outside reader PRs die. jellyfin-web's CONTRIBUTING requires the full PR template, and "failing to do so will result in the PR being closed as invalid without review". The template requires before/after screenshots, a "Code assistance" section naming the exact AI tool, model and version (or stating none was used), and a checkbox confirming you have **substantively reviewed another open web PR** ([PR template](https://github.com/jellyfin/jellyfin-web/blob/master/.github/pull_request_template.md)). The LLM policy goes further. LLM-generated text is banned in issues, comments and PR descriptions. Vibe-coded changes are rejected. You must explain and defend changes in your own words. Features need "multiple discrete commits", and files like `.claude` must never be committed ([LLM/"AI" Policies](https://jellyfin.org/docs/general/contributing/llm-policies)). Enforcement is real. In September 2026 maintainer thornbill closed #8423, a measured 99% EPUB open-time improvement, as "Invalid per llm policy and failing to read/follow contributing guidelines" ([PR #8423](https://github.com/jellyfin/jellyfin-web/pull/8423)). For an AI-assisted workflow, the practical rule is this: you can use AI for code if you disclose it, but every issue, PR description and review reply must be written by you, and you must understand every line.

The merge record for book-reader work is stark. In 2026, outside PRs were closed unmerged for a paged/scrolled toggle (#7843), PDF zoom and header (#7609), a keep-screen-on toggle (#8096), and EPUB resume and startup fixes (#8421, #8423). An earlier PDF zoom PR (#6825) sat from May 2025 with its author asking "can we merge this?" ([#7843](https://github.com/jellyfin/jellyfin-web/pull/7843); [#8096](https://github.com/jellyfin/jellyfin-web/pull/8096); [#6825](https://github.com/jellyfin/jellyfin-web/pull/6825)). The #7609 case shows the failure mode. dkanada asked the author to "clone the existing video OSD rather than use a new top header and pill shape" and to "look like a Jellyfin UI component and use React under the hood". The author reworked it. Six months later they gave up, writing that changes "probably wont merge before they get conflicts with other peoples changes". Meanwhile dkanada's own BookOsd PRs merged in July and August ([PR #7609](https://github.com/jellyfin/jellyfin-web/pull/7609)). Two outside reader PRs opened in September 2026, dark mode for PDF (#8518) and showing the OSD on keyboard navigation (#8478), had no human comments at query time ([#8518](https://github.com/jellyfin/jellyfin-web/pull/8518); [#8478](https://github.com/jellyfin/jellyfin-web/pull/8478)).

The broader numbers are less bleak. Over the last 12 months jellyfin-web merged about **366 non-bot PRs** and closed about 346 without merging. About 259 PRs are open, and 43 non-bot ones are over a year old. In a sample of recent merges, member PRs merged in a median 0.8 days while outside contributors waited a **median 11.1 days, with a 75th percentile of 45 days** and a maximum of 327 ([GitHub search, jellyfin-web](https://github.com/jellyfin/jellyfin-web/pulls?q=is%3Apr+is%3Amerged+merged%3A%3E%3D2025-10-19)). Many of the unmerged closures came from authors with no prior merges, including spam and LLM-policy closures, so the raw closure rate overstates the risk for a careful contributor. Book work from outsiders does land when it is small and away from the reader core. "Allow sorting books by index number" merged after 175 days, and "Expose used SeriesName for Books in Metadata Editor" merged after 14 ([#7482](https://github.com/jellyfin/jellyfin-web/pull/7482); [#8164](https://github.com/jellyfin/jellyfin-web/pull/8164)). Two gaps remain. Time-to-first-review was not measured because the API rate limit ran out, and the closure reasons for several reader PRs are unrecorded.

Release timing compounds the wait. jellyfin-web master is already at 13.0.0, so new features ship in the next major release ([package.json](https://github.com/jellyfin/jellyfin-web/blob/master/package.json)). Majors have arrived roughly yearly, and 12.0 spent June to August 2026 in release candidates. That puts 13.0 plausibly in mid-to-late 2027. This is an inference, since the project publishes no cadence statement.

## The winning path rides dkanada's published roadmap

dkanada has already said what comes next for the reader. He wants to move "settings, TOC management, maybe swipe and tap controls" into the React element, build "a unified page indicator", and extract "book navigation controls into a global helper function for user customization" ([PR #7848](https://github.com/jellyfin/jellyfin-web/pull/7848); [PR #8004](https://github.com/jellyfin/jellyfin-web/pull/8004)). His open PRs for a React TOC (#8330) and a unified progress indicator (#8320) occupy exactly the files you would touch. The project's own guidance is also explicit: "If you have a larger feature in mind please open an issue so we can discuss the implementation before you start" ([jellyfin-web README](https://github.com/jellyfin/jellyfin-web/blob/master/README.md)). The recommended sequencing follows from both.

First, spend a week or two building standing without code. Set up the dev loop. Write a hand-written issue that proposes a reader-settings panel inside BookOsd, cites the `scrolled-doc` TODO and the non-persisted settings, and lists the controls in priority order. Ask dkanada in the issue or on Matrix how he wants it shaped and whether it collides with #8320 or #8330. Review one or two open web PRs properly, which the template requires anyway and which builds goodwill.

Second, ship Tier 1 as a chain of single-focus PRs, each with screenshots and a disclosure section. Start with persisting the existing theme and font size to `CustomPrefs`. It is the smallest change, has the highest user value, and carries no design risk. Then add font family, line height and margins, then a real sepia and custom colors. Fixing the case-sensitive `.epub` extension check (the PDF check lowercases, the EPUB check does not) is a credible warm-up bug, though it was spotted from code reading and is untested ([plugin.js @v12.2](https://github.com/jellyfin/jellyfin-web/blob/v12.2/src/plugins/bookPlayer/plugin.js)).

Third, move to Tier 2: the scroll-mode toggle that #7843 attempted, tap zones and in-book search. Fourth, rather than proposing a parallel bookmarks API, help finish #15633 or the typed-position redesign dkanada sketched. That unblocks precise sync and sets the pattern a bookmark or annotation entity would follow. Raise a renderer swap to foliate-js only after you have merged work and a track record, as a jellyfin-meta discussion.

In calendar terms, assume roughly **2–4 weeks of focused effort to get the first one or two Tier 1 PRs merged**, with 1–3 months of elapsed time per PR given the 45-day contributor 75th percentile. Allow **4–6 months of part-time work to cover Tiers 1 and 2**, and a year or more before Tier 3 annotations exist, gated on core API decisions you do not control.

## Three escape hatches trade upstream reach for speed

If your real goal is reading your Jellyfin library well on iOS, the fastest route bypasses the built-in reader. Jellyfin's official **OPDS plugin** is maintained. v8 shipped on 2026-09-08 targeting the 12.0 ABI, and it exposes `/opds` with basic auth ([jellyfin-plugin-opds](https://github.com/jellyfin/jellyfin-plugin-opds)). KyBook 3 supports custom OPDS catalogs ([kybook-reader.com source](https://github.com/kolyvan/kybook-reader.com/blob/master/index.html)). There are caveats. No user report confirms the KyBook-plus-Jellyfin pairing. A plugin bug serves feeds as `text/plain` on 10.11 and the fix PR is still open. A competing vendor (so possibly biased) reports KyBook's OPDS breaking on newer iOS ([plugin issues](https://github.com/jellyfin/jellyfin-plugin-opds/issues); [justread.app](https://justread.app/en/posts/kybook-3-alternatives-iphone-2026)). Maintained OPDS readers such as Readest and KOReader are safer bets ([Readest](https://github.com/readest/readest)). The cost is that progress does not sync back to Jellyfin, and the built-in reader stays weak for everyone else.

**JavaScript Injector**, a community server plugin with builds for 10.11 and 12.0, injects scripts into the web UI. Other third-party plugins already depend on it ([Jellyfin-JavaScript-Injector](https://github.com/n00bcodr/Jellyfin-JavaScript-Injector)). It could add a settings panel that reaches into the epub.js rendition at runtime and ship this week with no review. However, server plugins have no official hook into web UI. Book-player internals are not a stable API and are being refactored right now. Plugins also must be rebuilt for every major release ([CONTRIBUTING.md](https://github.com/jellyfin/jellyfin-web/blob/master/CONTRIBUTING.md); [12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0/)). Expect breakage. The best use is as a prototype to show dkanada a working UX.

A **fork** of jellyfin-web, served from your own server via `JELLYFIN_WEB_DIR`, gives you full control, including a foliate-js swap ([Jellyfin docs: Development](https://jellyfin.org/docs/general/contributing/development)). The price is permanent rebasing against a reader area that changed weekly through mid-2026. It also helps only users of your server. A server plugin with its own controller and storage could host bookmarks and annotations without a core migration, but the team did not verify how web would discover it.

## Conclusion

The question "how much effort" splits into two very different numbers. The engineering number is small. A senior developer could match Audiobookshelf-level reading controls in about a month of evenings, because epub.js already exposes the hooks and Jellyfin already has server-synced per-user preferences. The social number is large and mostly outside your control. Over 2026, the reader effectively belonged to one maintainer, and outside work that didn't fit his architecture (or that broke the LLM rules) died regardless of quality. The deciding factor is therefore alignment rather than skill. Small PRs that implement dkanada's own published next steps, written and defended in your own words, have a realistic path. A KyBook-style feature drop does not.

The two goals are best pursued separately. For your own reading, set up OPDS with a maintained reader now, and don't wait for 13.0. For the community, treat upstream contribution as a slow, relationship-first project. Its highest-leverage single act is probably not a UI control but helping unstick the typed-position API in #15633, because bookmarks, highlights and precise sync all queue behind it. One unverified factor matters most for planning: whether dkanada wants outside help on the reader at all. A single issue comment will answer that faster than any further research.
