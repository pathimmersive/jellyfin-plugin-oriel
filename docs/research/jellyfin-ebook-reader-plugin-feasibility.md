# Build the reader beside Jellyfin, not inside it

Yes. A Jellyfin 12.0 server plugin can deliver a KyBook-class reader that you fully control, because nothing about the reader itself needs jellyfin-web's cooperation. A plugin controller can serve a full-screen single-page app at its own route (for example `/Reader/`) on the same origin as the web client, reuse the logged-in user's token from `localStorage["jellyfin_credentials"]`, stream the book through the existing library API, keep exact positions, bookmarks and highlights in its own SQLite or JSON store, and mirror a percentage into core user data so the Continue Reading row keeps working. The fragile part is getting *into* jellyfin-web. There is no supported UI extension point, and the maintainers refused to create one in 2023. A "Read" button or a takeover of the built-in book player therefore depends on the third-party File Transformation plugin and has to be treated as optional sugar on top of a reader that also works from a plain URL. On your iPhone, the reader works in Safari (and as a home-screen web app). Whether it works inside the official Jellyfin iOS app is the single most important unverified item. Native clients such as Swiftfin, Android TV and Roku will never see it. Build it on foliate-js (MIT) with a custom UI. Budget roughly **10–14 person-weeks for an iOS-quality MVP**, **18–26 for a full KyBook-3-class feature set**, and **1–2 person-weeks per Jellyfin major release** plus 2–4 weeks a year for engine and WebKit churn. In exchange you get a schedule you set yourself, unlike upstream, where no outside book-reader PR merged in 2026 and annotations are blocked on a stalled core API.

## A plugin can own everything except the jellyfin-web UI

Jellyfin 12.0 kept the extension model and broke binary compatibility. You still subclass `BasePlugin<TConfig>`, register services through `IPluginServiceRegistrator`, and drop in ASP.NET Core controllers. The server calls `AddApplicationPart(pluginAssembly)` for every plugin, so **any `ControllerBase` in your DLL becomes a live endpoint with its own `[Route]` and full constructor injection** ([ApiServiceCollectionExtensions.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Server/Extensions/ApiServiceCollectionExtensions.cs)). The break is the runtime: 12.0 targets **.NET 10, and plugins built for 10.11 do not load** ([12.0 release post](https://jellyfin.org/posts/jellyfin-release-12.0)). The official plugin template has not caught up. Its master still targets net9.0 against 10.11.5 packages, with a 12.x Renovate branch unmerged ([template csproj](https://github.com/jellyfin/jellyfin-plugin-template/blob/master/Jellyfin.Plugin.Template/Jellyfin.Plugin.Template.csproj)). Copy the official Playback Reporting plugin's setup instead: `net10.0`, `Jellyfin.Controller 12.*-*`, `targetAbi 12.0.0.0` ([Playback Reporting csproj](https://github.com/jellyfin/jellyfin-plugin-playbackreporting/blob/master/Jellyfin.Plugin.PlaybackReporting/Jellyfin.Plugin.PlaybackReporting.csproj)). A reader needs only `ILibraryManager`, `IUserDataManager`, `IUserManager` and the application paths. Of those, only `IUserManager` changed in 12.0, where `Users` became `GetUsers()`.

**Hosting the reader page.** Don't use `IHasWebPages` for the reader. Those pages render inside the dashboard shell, and the listing endpoint is admin-only ([DashboardController.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Api/Controllers/DashboardController.cs)). Serve the reader from your own controller out of embedded resources, the way Jellyfin Enhanced serves `js/{**path}` with `GetManifestResourceStream` ([JellyfinEnhancedController.cs](https://github.com/n00bcodr/Jellyfin-Enhanced/blob/main/Jellyfin.Plugin.JellyfinEnhanced/Controllers/JellyfinEnhancedController.cs)). jellyfin-web is served by the same server under `/web` ([Startup.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Server/Startup.cs)), so a plugin route is the same origin. Neither the 12.0 server nor jellyfin-web emits a Content-Security-Policy or X-Frame-Options header. That was established by grepping both codebases, not from documentation.

**Reusing auth.** jellyfin-web 12.0 still stores credentials through `jellyfin-apiclient` 1.11.0. The key is `jellyfin_credentials`, a JSON value with a `Servers[]` array that carries `AccessToken` and `UserId` ([ServerConnections.js](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/lib/jellyfin-apiclient/ServerConnections.js); [credentials.js](https://github.com/jellyfin-archive/jellyfin-apiclient-javascript/blob/master/src/credentials.js)). Your page reads that value and sends `Authorization: MediaBrowser Client="…", Device="…", DeviceId="…", Version="…", Token="…"`. Two 12.0 details matter. First, **legacy authorization is now off by default**, so `X-Emby-Token` and the `api_key` query parameter are rejected. Only the `MediaBrowser` header and the `ApiKey` query parameter (for `<img>`-style URLs) work ([AuthorizationContext.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Server.Implementations/Security/AuthorizationContext.cs); [GitHub release v12.0](https://github.com/jellyfin/jellyfin/releases/tag/v12.0)). Second, the HTML and asset endpoints must be anonymous, because a browser navigation cannot attach a header, while the data endpoints carry `[Authorize]`. That is the split Jellyfin Enhanced uses ([CatchUpController.cs](https://github.com/n00bcodr/Jellyfin-Enhanced/blob/main/Jellyfin.Plugin.JellyfinEnhanced/Controllers/CatchUpController.cs)). If no credentials exist, redirect to `/web/#/login`, and use relative URLs so a configured BaseUrl keeps working. The credentials key is an internal detail, not an API. jellyfin-web already depends on `@jellyfin/sdk`, and a future storage migration would break this silently, so isolate the lookup in one module.

**Storage.** A plugin cannot add tables to `jellyfin.db`. `JellyfinDbContext` applies configurations only from its own assembly ([JellyfinDbContext.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/src/Jellyfin.Database/Jellyfin.Database.Implementations/JellyfinDbContext.cs)). Core `UserData` has no free-form field for a CFI ([UserData.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/src/Jellyfin.Database/Jellyfin.Database.Implementations/Entities/UserData.cs)). The proven patterns are a **private SQLite file**, as Playback Reporting does with `playback_reporting.db` ([ActivityRepository.cs](https://github.com/jellyfin/jellyfin-plugin-playbackreporting/blob/master/Jellyfin.Plugin.PlaybackReporting/Data/ActivityRepository.cs)), or **per-user JSON files written atomically**, as Jellyfin Enhanced does ([UserConfigurationManager.cs](https://github.com/n00bcodr/Jellyfin-Enhanced/blob/main/Jellyfin.Plugin.JellyfinEnhanced/Configuration/UserConfigurationManager.cs)). For highlights and notes, use SQLite in `DataFolderPath`, keyed by (userId, itemId). Be careful with dependencies. The host already ships Microsoft.Data.Sqlite and EF Core, so bundle a separate wrapper or mark host assemblies `ExcludeAssets=runtime` to avoid load conflicts. Small display settings could instead live in core `DisplayPreferences.CustomPrefs`, which jellyfin-web's `userSettings.set(…, true)` already syncs per user ([userSettings.js](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/scripts/settings/userSettings.js)). Owning everything in your own store is simpler. **Unverified:** whether 12.0's built-in backup includes plugin data folders. Assume it does not, and add an export endpoint.

**Progress and Continue Reading.** You need no custom server code for this. `POST /UserItems/{itemId}/UserData` accepts `PlaybackPositionTicks` and `PlayedPercentage` ([ItemsController.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Api/Controllers/ItemsController.cs); [UpdateUserItemDataDto.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Model/Dto/UpdateUserItemDataDto.cs)). Server-side, the equivalent is `IUserDataManager.SaveUserData` ([IUserDataManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Controller/Library/IUserDataManager.cs)). The `Sessions/Playing`, `/Progress` and `/Stopped` routes are an alternative that would also surface the reader as an active session ([PlaystateController.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/Jellyfin.Api/Controllers/PlaystateController.cs)). The built-in 12.0 player encodes position as a fraction on a fake 1000 ms timeline and resumes with `cfiFromPercentage(startPositionTicks / 10000000)` ([bookPlayer/plugin.js @v12.0](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/plugins/bookPlayer/plugin.js)). The interop rule is therefore **write `round(fraction × 10^7)` ticks to core and keep the exact CFI in your store**. On open, prefer your CFI, unless core's position is newer because you read elsewhere, in which case fall back to its percentage. The home "resume" section already special-cases `mediaType === 'Book'` ([resume.ts](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/components/homesections/sections/resume.ts)). **Unverified:** whether `UserItems/Resume` needs `RunTimeTicks` set on Book items to list them, and how the server derives `PlayedPercentage` for books. The spike should test both.

### Reconciling the two file endpoints

The notes disagree on how to fetch the book. One recommends `GET /Items/{id}/Download`. The other prefers `GET /Items/{id}/File`. The disagreement is about permissions, not about facts. Both notes agree that `/Download` carries `[Authorize(Policy = Policies.Download)]` and that the user therefore needs download permission ([LibraryController.cs @v12.0](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Api/Controllers/LibraryController.cs)). One note adds a runtime `item.CanDownload(user)` check. The other found that `/File` needs only `[Authorize]`, but read it on `master`, not the v12.0 tag ([LibraryController.cs master](https://raw.githubusercontent.com/jellyfin/jellyfin/master/Jellyfin.Api/Controllers/LibraryController.cs)). The built-in reader uses `getDownloadUrl`, so **users without download permission cannot read in the stock reader either**. On a household server where you are the admin, the choice barely matters.

| Route | Permission | Pro | Con |
|---|---|---|---|
| `/Items/{id}/Download` | Download policy (+ `CanDownload`) | Same behaviour as stock reader; server enforces access | Fails for users denied downloads |
| `/Items/{id}/File` | Any authenticated user (master; **v12.0 unverified**) | Works for every user | Bypasses an admin's "no download" intent; library/parental visibility check **not verified** |
| Plugin's own stream endpoint | Whatever you enforce | Full control, can add range requests and caching | You must call `item.IsVisible(user)` yourself |

My recommendation is to use `/Download` by default, because it respects the server's existing permission model, and to fall back to a plugin endpoint that explicitly checks visibility only if some user lacks download rights. Don't rely on `/File` until the spike confirms, at the v12.0 tag, that it enforces library and parental access.

## Getting into jellyfin-web means betting on File Transformation

There are three ways to put the reader in front of users. Each one couples to jellyfin-web differently.

| Option | Mechanism | Coupling | Fragility |
|---|---|---|---|
| A. Standalone link | Direct URL, bookmark, `menuLinks` sidebar link, home-screen web app | None beyond the REST API | Lowest; works where injection is impossible |
| B. "Read" button | Injected script with DOM mutation observers adds a button on book detail pages | DOM structure and class names in Modern and Legacy layouts | High; layout churn breaks it silently |
| C. Player override | Patch `/web/config.json` `plugins` array to add a `window`-named player at priority ≤0 and inject a script defining it | `pluginManager` string spec, `config.json` schema, player interface | Moderate; uses unminified contracts, but depends on script-load timing |

Option C is the more elegant takeover, and it rests on real mechanics. `pluginManager.loadPlugin` accepts a string that names a `window` property holding an async factory. Startup reads the plugin list from `config.json`. playbackManager sorts players by ascending `priority` and picks the first whose `canPlayMediaType`/`canPlayItem` accept the item. The built-in `BookPlayer` sits at **priority 1 and claims only `.epub`** ([pluginManager.js](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/components/pluginManager.js); [playbackmanager.js](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/components/playback/playbackmanager.js); [config.json](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/config.json)). A thin player at priority 0 could therefore claim EPUBs, so that the existing Play and Resume buttons open your reader. The simplest version of that player would just navigate to `/Reader/?id=…` instead of implementing the full player interface in a dialog (my inference, untested). Two caveats apply. These files were read on `master`, not `v12.0`. More seriously, **nobody has tested whether an injected script defines `window.<Name>` before `loadPlugins()` runs**. If it doesn't, the config entry fails with only a console warning.

Options B and C both need injection, and the only working route in 2026 is IAmParadox27's **File Transformation** plugin. Version 3.0 shipped the same day as Jellyfin 12.0. It replaced its Harmony/MonoMod interception with ASP.NET Core middleware, added error isolation with fallback to the original response, and is at 3.0.2.0 ([FT releases](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/releases)). n00bcodr's JavaScript Injector 4.0 layers script registration on top of it ([JS Injector](https://github.com/n00bcodr/Jellyfin-JavaScript-Injector)). The track record is mixed. FT 2.5.4.0 crashed Jellyfin 10.11.6 at startup ([FT #46](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/issues/46)), and its author calls plugins "strictly 1 version compatible". Writing `index.html` to disk, as mrozio1's reader does, is lost on every Docker image update and fails on read-only filesystems ([jellyfin-plugin-bookreader](https://github.com/mrozio1/jellyfin-plugin-bookreader)).

The maintainer stance is clear and dated. In 2023 the core team closed PR #9095, which proposed an official file-transformation service. nielsvanvelzen wrote "We don't support such modifications and we should not make it easier to do it in an 'official' way" ([PR #9095](https://github.com/jellyfin/jellyfin/pull/9095)). When third-party plugins break, the team sends users back to the plugin author ([jellyfin#16905](https://github.com/jellyfin/jellyfin/issues/16905)), and for 12.0 it told users to remove third-party plugins before upgrading ([release post](https://jellyfin.org/posts/jellyfin-release-12.0)). Injection is tolerated, not supported, and that is unlikely to change. The design conclusion is to **make option A the product and C a soft dependency**: detect File Transformation via reflection, patch only `config.json` plus one script when it is present, and never patch minified bundles.

## Your iPhone gets the reader; native apps never will

The reader runs wherever jellyfin-web's origin and localStorage are available. In Safari on iOS it works by construction. That browser is the main target, and Thorium Web's notes flag the constraints to design around: **no Fullscreen API on iPhone** and iPadOS font-size quirks ([thorium-web README](https://github.com/edrlab/thorium-web)). The official Android app is explicitly "only a web wrapper" over the server's web client, so injected UI and the plugin page should reach it ([jellyfin-android README](https://github.com/jellyfin/jellyfin-android)). The 12.0 fix "book player fullscreen on mobile apps" shows that the web reader already runs inside the mobile wrappers ([jellyfin-web releases](https://github.com/jellyfin/jellyfin-web/releases)). For the **official iOS app, no 2026 source confirms that it loads the server-hosted web UI** or that a navigated plugin page shares its localStorage. Test this on day one. If it fails, the Safari or home-screen path is still a complete answer for you. Swiftfin does not support book libraries at all ([Swiftfin libraries.md](https://github.com/jellyfin/Swiftfin/blob/main/Documentation/libraries.md)). Android TV, Roku and Swiftfin "don't run web-client scripts" and get no Read button ([jellyfin-plugin-bookreader](https://github.com/mrozio1/jellyfin-plugin-bookreader)). Jellyfin Media Player and the newer desktop app reportedly need `ForceExternalWebclient`-style settings to load server-side customization, based on dated community reports ([Jellyfin forum](https://forum.jellyfin.org/printthread.php?tid=7514)).

## foliate-js with a custom UI beats Readium or a Readest fork

**foliate-js is the engine to build on.** It is MIT-licensed, parses EPUB, MOBI, AZW3, FB2 and CBZ entirely in the browser, and ships paginator, CFI, highlight-overlayer, search, TTS, footnote and dictionary modules in about **6–7k lines**. You can vendor and patch it ([foliate-js](https://github.com/johnfactotum/foliate-js)). It needs no server-side manifest, so the plugin only streams the raw file. Its costs are stated in its own README: "not stable. Expect it to break and the API to change at any time". There are no releases, so you pin a commit. Its CSS-column pagination is slow on large chapters, and iOS Safari is not an official target. The strongest iOS evidence is indirect: Readest ships its own foliate-js fork on iOS through Tauri's WKWebView ([Readest](https://github.com/readest/readest)).

**Readium ts-toolkit** (BSD-3) is better maintained, with releases 2.10 through 2.13 in about four weeks of autumn 2026. But its navigator requires a Readium Web Publication Manifest and a Positions List from a server ([npm @readium/navigator](https://registry.npmjs.org/@readium/navigator); [thorium-web Implementers Guide](https://github.com/edrlab/thorium-web)). **No .NET Readium streamer exists** ([Readium streamer doc](https://readium.org/technical/r2-streamer-doc/)). Choosing it adds an estimated 2–4 person-weeks to write one in C#, and you would track a fast-moving pre-maturity API. Thorium Web (BSD-3, `@edrlab/thorium-web` 1.7.0) offers a polished embeddable React reader, but its documented features stop at typography and themes, with no TTS, search or annotations. It also pulls React 19 and a heavy dependency stack ([npm @edrlab/thorium-web](https://registry.npmjs.org/@edrlab/thorium-web)).

**Forking Readest** buys near-instant feature parity: typography, TTS, dictionary, annotations, search and KOReader sync. The price is about **263k lines of Next.js/Tauri app code** (57k in the reader layer alone), a project that commits daily, and **AGPL-3.0** ([Readest](https://github.com/readest/readest)). The license point matters because Jellyfin plugins link GPLv3 NuGet packages and are effectively GPLv3 ([plugin template README](https://raw.githubusercontent.com/jellyfin/jellyfin-plugin-template/master/README.md)). MIT and BSD components fold in cleanly. AGPL code can be combined with GPLv3, but the network clause then obliges anyone serving the modified reader to offer its source. That reading of the GPL and AGPL comes from the research team and is not legal advice. An estimated 4–8 weeks of initial stripping plus perpetual rebasing makes the Readest fork the wrong trade for a solo developer who wants control.

PDFs and comics are a side concern. foliate's PDF adapter is experimental and pinned to PDF.js 5.5.207, and the stock 12.0 players for PDF and comics are now decent. Claim only EPUB (and later MOBI, AZW3 and FB2) in your reader, and leave the rest to Jellyfin.

## Ten weeks to a daily driver, a weekend every September

The estimates below decompose the work for one experienced developer using foliate-js and a lightweight custom UI. They come from feature breakdown and code-size anchors, not measured effort. Foliate's demo UI is 239 lines and Readest's reader layer is about 57k. The MVP implies roughly 8–15k lines of your own code.

| Phase | Scope | Person-weeks (est.) |
|---|---|---|
| 0. Spike | See next section | ~1 |
| 1. Shell | net10 plugin, embedded-asset controller, storage API (SQLite), GitHub Actions build, `manifest.json` repo | 2–3 |
| 1. Reader core | Open, paginate/scroll, tap zones, swipe/keys, TOC, progress and location | 3–4 |
| 1. Typography | Font family (bundled fonts), size, line height, margins, justify/hyphenate, themes, publisher-style override, persistence | 2–3 |
| 1. Sync | CFI in plugin store, ticks mirrored to `UserData` for Continue Reading | 1–1.5 |
| 1. iOS polish | Safe areas, gesture/selection conflicts, big-chapter performance, home-screen web app | 2–3 (partly in MVP) |
| **MVP total** | Shell + core + typography + sync + bookmarks + basic iOS polish | **~10–14** |
| 2. Annotations | Highlights, notes, colors, Markdown/JSON export | 3–4 |
| 2. Search, TTS, dictionary | `search.js`, Web Speech via `tts.js`, Wiktionary via plugin proxy or StarDict via `dict.js` | 3–5.5 |
| 2. Entry point | File Transformation `config.json` override or Read button, with standalone fallback | 1–2 |
| 2. Extra formats, tests, docs | MOBI/AZW3/FB2, accessibility | 2–4 |
| **Full total** | KyBook-3-class | **~18–26** |
| Maintenance | Retarget and rebuild per Jellyfin major, interface fixes, entry-point repair | **1–2 per major** |
| Maintenance | foliate-js pin updates, WebKit regressions | **2–4 per year** |

At ten hobby hours a week, the MVP is roughly ten to fourteen months of calendar time. Keep that in mind before comparing it with the upstream path. Majors have landed roughly yearly: 10.11 in 2025, 12.0 in September 2026, and 12.1 and 12.2 within weeks of it ([jellyfin tags](https://github.com/jellyfin/jellyfin/tags)). Every recent major changed the .NET runtime or Controller interfaces. A plugin that loads against the wrong ABI flips to `NotSupported` on a type-load error rather than failing to install ([PluginManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Emby.Server.Implementations/Plugins/PluginManager.cs)). Distribution is a self-hosted `manifest.json` with per-ABI entries and MD5 checksums, and there is no signing ([InstallationManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Emby.Server.Implementations/Updates/InstallationManager.cs)). Jellyfin Enhanced shows the dual-target pattern of one source, two builds and one manifest ([JE manifest.json](https://github.com/n00bcodr/Jellyfin-Enhanced/blob/main/manifest.json)). Don't expect an official-catalog listing. A core team member said in 2025 that third-party plugins generally "wouldn't fit our official offer" but can be added to the docs' third-party list ([forum](https://forum.jellyfin.org/t-can-my-plugin-be-included-in-the-official-manifest)). The server-side maintenance is predictable and small. The unpredictable cost is anything that touches jellyfin-web internals, which is why the design keeps that surface to one `config.json` patch and one script.

Compare that with upstream. Tier-1 typography could be coded in 1.5–3 weeks against the existing epub.js reader, but outside reader PRs were closed unmerged throughout 2026. Outside contributors wait a median of 11 days and a 75th percentile of 45 days, and bookmarks and highlights cannot exist until core PR #15633's typed-position API is settled ([PR #15633](https://github.com/jellyfin/jellyfin/pull/15633); [PR #7609](https://github.com/jellyfin/jellyfin-web/pull/7609)). The plugin costs several times more engineering, and in exchange it removes every external gate.

## Prior art proves the shape and leaves the niche open

**mrozio1/jellyfin-plugin-bookreader** is the closest precedent and a ready reference architecture: a plugin-hosted reader at `/BookReader/Reader?id=…` with epub.js, pdf.js and comic modes, Calibre conversion for MOBI and AZW3, themes, two-page spreads, server-synced position, a Read button injected into `index.html`, and an optional Play-button takeover. It also has 3 commits, 0 stars, no releases, and targets **10.11/.NET 9 only**, so it will not load on 12.0 ([repo](https://github.com/mrozio1/jellyfin-plugin-bookreader)). Read its code, but don't build on it. **JellyBook** is a Flutter mobile app that reads from Jellyfin but documents a Bookshelf dependency, and Bookshelf is deprecated in 12.0. Its 12.0 compatibility is unverified ([JellyBook](https://github.com/JellyBookOrg/JellyBook)). The official **OPDS plugin** shipped a 12.0 build on release day ([jellyfin-plugin-opds](https://github.com/jellyfin/jellyfin-plugin-opds)) and lets Readest or KOReader read your library today. Progress does not flow back to Jellyfin, and one user notes it lacks per-library catalogues ([MobileRead](https://www.mobileread.com/forums/showthread.php?t=368857)). A March 2026 survey of more than 60 Jellyfin plugins listed no reader plugin at all ([JellyWatch](https://jellywatch.app/blog/awesome-jellyfin-plugins-complete-guide-2026)). The bar did rise, though. 12.0 moved Bookshelf's metadata into core and redesigned the reader across formats ([release post](https://jellyfin.org/posts/jellyfin-release-12.0)), so your differentiators are typography, exact sync, annotations, search, TTS and dictionary, not basic reading.

## Five unknowns to kill in the first week

The risks are concentrated rather than spread out. The **iOS app WebView** might not share jellyfin-web's origin or localStorage. **foliate-js on iOS Safari** might stutter on large chapters or fight long-press selection inside iframes. The **`jellyfin_credentials` format** can change in any web release. **Script-load timing** might defeat the `config.json` player override. And **Continue Reading** might not list books written via `UserData` without `RunTimeTicks`. Less likely but real: an admin's reverse-proxy CSP could block the `blob:` workers and iframes the engine needs, and plugin data may be missing from Jellyfin backups.

A one-week spike settles all of them. Build a net10 plugin with one anonymous controller serving a static page at `/Reader/` and one `[Authorize]` endpoint that echoes `User.GetUserId()`. In the page, read `jellyfin_credentials`, fetch an EPUB via `/Items/{id}/Download`, and render it with a pinned foliate-js commit. Write `round(fraction × 10^7)` to `UserItems/{id}/UserData` and confirm that the book appears in Continue Reading and that the stock reader resumes nearby. Then open the page on your iPhone three ways: in Safari, as a home-screen web app, and from inside the official Jellyfin iOS app. On each, test page turns on a 5 MB omnibus and long-press selection. Install File Transformation 3.0.2, patch `config.json` to add a priority-0 `window` player that redirects to `/Reader/`, and check whether the injected script wins the race against `loadPlugins()`. Finally, call `/Items/{id}/File` as a user without access to the library to settle the permission question at the v12.0 tag.

## Conclusion

The plugin route reframes the problem. Upstream, the obstacle was people: one maintainer's architecture and a stalled API. In a plugin, the obstacle is a single trust boundary, jellyfin-web's front end, which you do not control and the maintainers will not open. Everything behind that boundary is yours: the reader, storage, sync and release cadence. So the winning design treats jellyfin-web as a launcher you may or may not get, never as a host. That also means the project's value hinges less on Jellyfin than it seems. A reader at `/Reader/` that authenticates against Jellyfin and stores annotations in its own database is effectively a self-hosted Readest for your library, and the core of it would survive even if injection died entirely.

Two practical implications follow. First, the spike's iOS-app result decides how ambitious phase 1 should be. If Safari or a home-screen web app is your real reading surface, skip the entry-point work and spend those weeks on typography and iOS polish. Second, the plugin and upstream need not compete. Once your reader exists, its exact-position storage and the tick-mirroring convention are concrete evidence you could bring to the #15633 typed-position discussion. Contributing from a working implementation is a far stronger position than proposing from scratch.
